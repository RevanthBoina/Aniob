## Phase 1 — Source audit and baseline mapping (historical)

The following tables record the pre-implementation baseline. Their “planned change” column is historical; current status and remaining work are tracked after the Parts 1–8 sequence below.

### Architecture comparison outcome

The architecture review reinforced useful boundaries rather than a code-copy approach: a platform-neutral task loop; Android-specific observation and dispatch behind adapters; separate policies for batching, approvals, retries, and reporting; and unit tests around those boundaries. Aniob already has several of these seams. The main gap is that the Android ViewModel still wires and owns too many of them, so the next phase should extend the existing seams rather than replace them.

## Requested implementation sequence (Parts 1–8)

1. **Part 1 — One interruption policy:** add pure-core `AskPolicy`; map the persisted three-level setting without silently re-arming OFF; make approval wait/cancellation explicit with no timeout denial; post the task-start heads-up; implement the two-miss same-target question through the existing ask channel.
2. **Part 2 — One completion surface:** remove pill code/lifecycle/preference; keep the ongoing/result notification; open chat only for failure or unverified completion; support notification RemoteInput and quick choices.
3. **Part 3 — Capability first:** resolve real intents before any chooser/question/model; remove invented destination/contact/app choices; run local device queries and system AppOps through actual installed inventory; keep model assets out of the APK.
4. **Part 4 — Honest outcomes:** centralize user copy in `AniobOutcomeCopy`; preserve raw reason codes only in logs/research/outcome records; keep FAILED for partial completion and preserve the rejected-Finish cap.
5. **Part 5 — Task-scoped state:** remove process-wide retry memory, begin a per-task ledger at task start, and retain only hard policy blocks as hard blocks.
6. **Part 6 — Build gating:** gate research Settings and benchmark controls on `FLAG_DEBUGGABLE`; force release behavior to full capability mode; keep all ablation rows in developer telemetry.
7. **Part 7 — Preserve/strengthen invariants:** recompute identity from fresh nodes; verify visible effects; rewrite HOME/BACK/RECENTS against system-owned targets; distinguish safe re-plan from hard safety stop; support bounded 2–8 grounded members, repeats, snapshot-bound re-grounding, number normalization, and parameterized replay templates.
8. **Part 8 — Consolidate seams:** retain one burst executor and one `StepPipeline` dispatch path; extract `CompletionReporter`, build policy, `TaskRunner`, `ApprovalCoordinator`, telemetry sink, and `SessionState` one at a time; add typed `ScreenId` without collapsing structural/content/replay identity semantics.
